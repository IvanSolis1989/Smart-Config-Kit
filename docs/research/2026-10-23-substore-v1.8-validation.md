## 本次失败保护与回归

1. 原实现本机 local 预览后，`content` 相同或 dry run 可直接返回，漏掉预览期间的手工编辑。现在返回前重新读取完整条目；变化则 `concurrent_change`，零写入、零备份，不宣称成功。
2. 原实现写前比较之后仍需等待备份与权限 checkpoint。若期间用户改动 content，旧值可能被覆盖；改动 process 时也可能在写后才发现。现在备份之后、发送之前再次完整读回比较，更新和恢复均适用，冲突零写入。Cloudflare 同样前置检查，并继续保留服务端原有完整 revision 保护。
3. 新增备份失败零写入、成功应答却未持久化不能成功的回归。
4. 新增扩展客户端→权限 transport→实际 restricted route→实际 executeLocalSnapshotOperation 的跨模块测试：content 提交、独立读回、恢复、dry run、处理失败、权限拒绝、并发编辑、响应丢失、服务端及客户端读回不一致。适配器的处理/存储是合成 fixture，不冒称原生引擎或 Cloudflare。

本机 API 不提供原子条件 PATCH；新增 GET 只能缩小竞态窗口，无法消除最后一次 GET 与 PATCH 之间的竞争。验收期间避免同时手工编辑同一条目。写入响应丢失或读回失败时保留备份并标记结果未知，先独立读回，不能盲重试。

## 真实链路执行清单与通过标准（本轮均待执行）

在用户自行控制的环境进行，下列步骤不要求向维护者提交任何 URL、节点或密钥。先用隔离测试实例/条目验负向场景，再进行真实账号正向验收；不要为测试故意耗尽生产一次性链接、破坏生产快照或修改生产发布合约。

### A. 固定安装与私密基线

1. 记录扩展完整 commit、manifest 版本、浏览器版本、本机 Sub-Store 版本、Worker build/deployment ID 及所用 patcher 版本。由已审查 commit 通过 package.mjs 生成目录（README 的 `--out` 绝对路径命令），检查包后在扩展管理页面原目录 Reload。
2. 用户私密备份两端目标单订阅、process、collections 与已发布物；记录逐源最低节点数、必需来源前缀、当前发布者和真实发布文件。不要用旧六站数字作为永不变化的新阈值。
3. 所有地址与密钥只在自己的可信 UI/私有配置中输入。不要写进命令行参数、CI、Issue、PR、终端回显或公开收据；测试后清理本机敏感备份需遵循自己的恢复保留策略。
4. 通过标准：安装版本确证为本次 commit；真实浏览器原生首次授权成功，未许可的来源不产生后端写入；准备完毕才开始源验收。

### B. 本机与 Cloudflare remote 单源

1. 用户人工登录已授权机场，正常进入仪表盘，不按同步按钮。观察本轮独立两端结果，分别在对应 Sub-Store 管理前端重新打开单订阅，发起新的后端读取（不能只看扩展旧成功状态）。
2. 核对预期新 URL、process、source、其他字段、collections 全部符合基线；本机和 Cloudflare 分别原生 noCache 预览，原始及处理后均达到预先定义最低量且无错误占位。对未换链的来源要记录“本轮预览＋读回未变化”，而不是复用旧收据。
3. 隔离测试中让云端不可用，确认本机成功仍保留、云端错误；反向验证本机失败不伪造云端通过。云端配置权限和机场许可分别撤销测试。
4. 通过标准：每端均有当前运行时间、正确目标、独立读取和原生预览证据；只改 URL；部分成功不能记为双端通过。中断写入先读取现状，确认有无落盘，再由用户决定恢复或重试。

### C. 受阻 remote 快照

1. 在测试部署对已明确允许来源确认实际直连为 403 challenge。扩展准备本机 original 快照后，独立 GET 策略入口，仅私密检查 `available/nodeCount/capturedAt/expiresAt/urlMatchesCurrent`；再在真实云端 noCache 预览此源。
2. 关闭本机服务和浏览器，重新请求云端单源及集合，确认使用已保存原始快照并执行云端自己的 process；健康来源不得靠该快照绕过正常下载。
3. 测试部署分别验证：无快照、过期超过24h、候选超过120s且未成为持久 URL、URL/处理器/UA 改变、普通401/403/500、网关200包装403均不得成为快照成功。等候/改变时间或夹具仅用于测试环境；实际 KV TTL 冷读仍需真实时间验证。
4. 通过标准：允许的 challenge 场景可用，其他场景失败关闭；旧发布副本仍受发布合约保护。证明的是限期保存和处理能力，不是原站对 Cloudflare 限制已消失。

### D. 一次性链接持久 local 内容

1. 确认受信站点、精确唯一名称、local＋空 URL 及两端策略最低节点数。用户取得新的测试一次性链接，观察一轮同步；用不含链接值的本机请求计数证明 remote 捕获恰好一次。
2. 两端独立读取 local 条目，确认 `content` 为该次 original、URL 仍为空、source 仍 local、process 与组合关系不变；各端原生 local 预览达到最低量。确认条件恢复备份按目标保存，不复制一次性链接为 remote。
3. 隔离环境在预览或备份时编辑条目，应冲突且不覆盖；模拟处理失败或响应丢失，应保留旧内容或明确未知，不自动重烧；验证两端各自条件恢复，手工修改后拒绝旧备份恢复。
4. 关闭本机超过24h，再从真实云端 noCache 输出/集合生成；内容仍可读，但记录快照捕获时间，不能称“自动刷新到最新”。重新开启本机取得下一份链接后另做一次刷新验收。
5. 通过标准：一次捕获、双端独立原生处理/读回、写入限于 content、持久云端输出、失败保护和条件恢复全部通过。

### E. 集合→Gist→Fusion

1. 两端单源通过后，在实际发布者使用的后端重新生成真实 Collection（noCache/严格失败设置）；检查每个必需来源的实际节点覆盖、处理顺序及去重/过滤后结果。不得用原始数量之和代替生成后数量，也不能只看总数。
2. 用户在原发布工具执行一次发布；独立读取 Gist 目标文件的本轮 revision/更新时间和实际内容，在本机私密比较它与集合输出。仅 HTTP200、旧文件仍可下载或发布任务退出0均不足以通过。此操作必须由有真实发布账户的用户执行。
3. 使用手机客户端的最终 download 入口独立请求 Fusion，检查内容覆盖及本轮一致性；若响应有 `X-SCKI-Source`，`gist` 才能用于新发布正向证据；`saved-replica` 应记“恢复旧副本”。revision 头如仅描述同步状态，还须核对响应 body，不能把该头当内容哈希。
4. 测试部署发布缺一个来源或错误占位的候选，应拒绝新内容且不覆盖已验收副本；无可用副本时503。有恢复合约时须明确其可能允许较旧较少的来源，只能记恢复通过。不要在生产 Gist 制造缺源。
5. 通过标准：真实集合正确、本轮 Gist 文件已更新、最终 Fusion body 与该轮发布物相符，并完成失败回退验证；分别记录生成、写入、分发结果。

### F. 手机拉取

1. 记录手机型号、系统、客户端版本和目标配置；只使用 download 入口。电脑/本机服务关闭，手机切到蜂窝网络主动刷新一次，核对客户端显示的本轮更新时间和实际来源覆盖/节点数量。
2. 在手机私密导出或使用应用诊断与本轮发布内容核对；若客户端会格式转换/过滤，说明预期差异。验证至少每个必需来源有节点进入目标池，必要时逐源选一节点测试连接。应用覆写时还须检查最终配置与组引用，不以订阅下载成功代替加载成功。
3. 通过标准：手机真实获取本轮发布物、配置可加载、覆盖达标、抽样连接通过；无法导出核对时明确证据不足。缓存旧节点仍能上网不能证明本轮刷新成功。

## 收据模板与对外边界

每个阶段单独填 `通过/失败/未执行/阻塞`：日期时间与时区、完整代码 commit、组件版本、目标代号、操作、原始/处理后数量、必需来源覆盖数、写入字段、非目标字段保持、独立读回、失败场景、结论。阶段没有证据就写未执行，整链通过必须 A–F 所有适用项均有本轮收据。

公共记录仅包含代码提交、组件版本、脱敏代号、数量、布尔检查及测试结果。订阅 URL、token、UUID、节点密码、管理路径、原始内容及其私人哈希均不公开；私密比较留在用户设备。没有访问真实账户、Cloudflare 管理资源或手机，因此本文不签发这些阶段的新验收。
