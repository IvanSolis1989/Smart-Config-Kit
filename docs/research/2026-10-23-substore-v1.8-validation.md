## Failure protection and regressions in this patch

1. Previously, unchanged `content` or dry run could return immediately after local preview, missing manual edits during that preview. The full entry is now reread before returning. Changes produce `concurrent_change`, zero writes and backups, and no success claim.
2. The old pre-write comparison still preceded backup and permission checkpoints. Content changes during that interval could be overwritten; process changes might only be detected after writing. A second full readback comparison now runs after backup and before sending, for both updates and restores. Conflicts produce zero writes. Cloudflare gets the same preliminary check while retaining its existing full server-side revision protection.
3. New regressions require zero writes when backup fails and reject success responses that were not actually persisted.
4. New cross-module tests run extension client → authorized transport → actual restricted route → actual executeLocalSnapshotOperation, covering content submission, independent readback, restore, dry run, processing failure, permission denial, concurrent edits, response loss, and mismatched server/client readbacks. Adapter processing/storage are synthetic fixtures, not native-engine or Cloudflare acceptance.

The local API has no atomic conditional PATCH. Additional GETs narrow but cannot eliminate the race between the last GET and PATCH. Avoid concurrent manual editing of the same entry during acceptance. Lost write responses or failed readbacks retain backups and mark the outcome unknown. Read independently before retrying; do not retry blindly.

## Real-chain execution checklist and pass criteria (all pending this round)

Perform these steps in a user-controlled environment. No URLs, nodes, or keys need be submitted to maintainers. Test negative cases on isolated instances/entries before positive real-account acceptance. Do not deliberately exhaust production one-time links, damage production snapshots, or alter production publication contracts for testing.

<a id="a-固定安装与私密基线"></a>
### A. Pin installation and private baselines

1. Record the full extension commit, manifest version, browser version, local Sub-Store version, Worker build/deployment ID, and patcher version. Generate the directory from a reviewed commit with package.mjs using the README’s absolute `--out` command; inspect the package and Reload the original directory in extension management.
2. Privately back up target individual subscriptions, process, collections, and published artifacts on both backends. Record per-source minimum node counts, required source prefixes, current publisher, and actual published file. Do not treat earlier six-site counts as permanently fixed new thresholds.
3. Enter addresses and keys only in trusted private UI/configuration. Do not put them in command arguments, CI, Issues, PRs, terminal output, or public receipts. Follow your own recovery-retention policy when cleaning sensitive local backups afterward.
4. Pass: installation confirmed at this commit; real browser-native initial permission succeeds; unauthorized origins produce no backend writes. Begin source acceptance only after preparation is complete.

<a id="b-本机与-cloudflare-remote-单源"></a>
### B. Local and Cloudflare remote single sources

1. Manually sign in to an authorized provider and open its dashboard normally, without pressing sync. Observe this round’s separate backend results. Reopen the individual subscription in each Sub-Store management frontend and initiate a new backend read, rather than relying on the extension’s old success state.
2. Verify expected new URL, process, source, other fields, and collections against the baseline. Perform native noCache previews on local and Cloudflare separately: both original and processed output must meet predefined minimum counts without error placeholders. For unchanged links, record “this round’s preview and readback unchanged,” not an old receipt.
3. In isolation, make cloud unavailable and verify that local success remains while cloud reports an error. Conversely, local failure must not fabricate cloud success. Test revoking cloud-configuration and provider permissions separately.
4. Pass: each backend has current run time, correct target, independent readback, and native-preview evidence; only URL changed. Partial success is not dual-backend success. After interrupted writing, read current state first to establish persistence, then let the user decide restoration or retry.

<a id="c-受阻-remote-快照"></a>
### C. Blocked-remote snapshots

1. In a test deployment, confirm actual direct access produces a 403 challenge for an explicitly allowed source. After the extension prepares the local original snapshot, independently GET the policy entry, privately inspecting only `available/nodeCount/capturedAt/expiresAt/urlMatchesCurrent`; then preview the source with real cloud noCache.
2. Shut down the local service and browser, request the cloud single source and collection again, and confirm use of the saved original snapshot with cloud’s own process. Healthy sources must not use snapshots to bypass normal downloads.
3. Separately test no snapshot, expiration beyond 24h, candidates beyond 120s that never became persistent URLs, changed URL/processor/UA, ordinary 401/403/500, and gateway-200-wrapped-403. None may count as snapshot success. Waiting/time changes/fixtures apply only to testing; actual KV TTL cold reads still need real elapsed-time validation.
4. Pass: allowed challenge cases work and others fail closed; old published replicas remain contract-protected. This establishes time-limited retention and processing, not removal of the origin’s Cloudflare restrictions.

<a id="d-一次性链接持久-local-内容"></a>
### D. Persistent local content from one-time links

1. Confirm trusted site, exact unique name, local with empty URL, and both backends’ policy minimum counts. Obtain a new test one-time link and observe one synchronization round. A local request count containing no link value must establish exactly one remote capture.
2. Independently read both local entries: `content` must be that capture’s original, URL still empty, source still local, and process/composition unchanged. Native local previews on both backends must meet minimum counts. Confirm target-specific conditional-restoration backups; do not copy the one-time link into a remote source.
3. In isolation, edit an entry during preview or backup: conflict must prevent overwrite. Simulated processing failures or lost responses must retain old content or explicitly mark unknown, without automatically consuming the link again. Verify each backend’s conditional restore and rejection of an old-backup restore after manual editing.
4. Shut down local services for more than 24h, then generate real cloud noCache output/collections. Content should remain readable, but record capture time; do not call it “automatically refreshed to latest.” After restarting local services and obtaining another link, perform a separate refresh acceptance.
5. Pass: single capture, independent native processing/readback on both backends, content-only writes, persistent cloud output, failure protection, and conditional restore all pass.

<a id="e-集合gistfusion"></a>
### E. Collection → Gist → Fusion

1. After both backends’ single-source checks pass, regenerate the actual Collection in the backend used by the real publisher, with noCache/strict failure settings. Check actual node coverage for every required source, processing order, and post-deduplication/filtering results. Neither summing raw counts nor checking only total count suffices.
2. The user publishes once through the original publishing tool. Independently read this round’s revision/update time and actual target-file content from Gist, privately comparing it locally with collection output. HTTP200, an old file still downloading, or publisher exit 0 is insufficient. This step requires a user with the real publishing account.
3. Independently request Fusion through the phone client’s final download endpoint. Check coverage and consistency with this publication. If `X-SCKI-Source` is present, only `gist` supports new-publication positive evidence; record `saved-replica` as “old-replica recovery.” A revision header describing only synchronization state also requires response-body comparison; it is not a content hash.
4. In a test deployment, a candidate missing a source or containing error placeholders must be rejected without overwriting the accepted replica; no valid replica yields 503. A recovery contract may allow older/fewer sources and counts only as recovery success. Do not remove sources from production Gist for testing.
5. Pass: correct actual collection, this round’s updated Gist file, final Fusion body matching the publication, and verified failure fallback. Record generation, writing, and distribution separately.

<a id="f-手机拉取"></a>
### F. Phone retrieval

1. Record phone model, OS, client version, and target configuration; use only the download endpoint. With the computer/local services off, switch the phone to cellular and explicitly refresh once. Check this round’s displayed update time and actual source coverage/node count.
2. Privately export on the phone or use app diagnostics to compare against the publication. Explain expected client format-conversion/filtering differences. Verify at least one node from each required source enters its target pool; test a node per source where needed. If applying overrides, also inspect final configuration and group references. Subscription download success is not loading success.
3. Pass: the phone actually retrieves this round’s publication, loads its configuration, meets coverage requirements, and passes sampled connections. If content cannot be exported/compared, state the evidence gap. Cached old nodes still connecting does not prove this refresh succeeded.

## Receipt template and disclosure boundaries

For each stage, independently record `pass/fail/not executed/blocked`: date/time/timezone, complete code commit, component versions, target alias, operation, original/processed counts, required-source coverage, written fields, preservation of unrelated fields, independent readback, failure cases, and conclusion. Without evidence, mark not executed. Whole-chain success requires current-round receipts for every applicable A–F item.

Public records contain only code commits, component versions, redacted aliases, counts, boolean checks, and test results. Do not publish subscription URLs, tokens, UUIDs, node passwords, management paths, raw content, or their private hashes; private comparisons stay on the user’s device. No real accounts, Cloudflare management resources, or phones were accessed, so this report grants no new acceptance for those stages.

This change modifies only the SubStore auxiliary tool, tests, and documentation, not rule graphs, DNS, proxy groups, filtering/classification logic, or derived client artifacts. AGENTS.md §0.1 therefore does not require regeneration of fourteen rule-artifact categories. Full-repository rule-contract checks are not listed as executed for this change.
